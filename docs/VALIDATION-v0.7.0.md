# v0.7.0 상태 복구·탐색·스레드 배경 검증 — 2026-10-06

상태: 요청한 기능 구현 완료. Release 빌드 경고 0/오류 0, 전체 자동 회귀 271/271 통과. 합성 100 MiB 파일·다중 탭·긴 한 줄·10만 검색 결과·취소와 비표시 WPF dispatcher 지연을 측정했다. 작은 창의 100/125/150/200% bitmap 렌더와 필터 0건 복구 화면을 확인했다. 실제 GUI 입력과 모니터 DPI 확인은 미실행이다.

## 구현

- 진행 `WorkStatus`와 항상 보이는 마지막 결과 `OperationStatus` 분리. 완료·취소·붙여넣기 거절·강조 제한·오류에 다음 행동 안내. 오래된 진행이 새 결과를 덮어쓰지 않는다.
- 강조 관리의 추가/적용 분리, 등록 행의 문구·색·사용 여부 직접 편집. 취소는 기존 규칙 유지. 최대 8개·문구당 4,096자·공백만인 입력 거절.
- 필터 0건의 스레드/내용/복합 원인 안내, 내용만 해제와 모든 필터 해제. 접힌 헤더에 적용·미적용 변경 표시.
- Ctrl+Shift+T 닫은 탭 복원. 원문·범위·필터·북마크·강조·검색·시간·문맥·커서·선택·스크롤과 탐색 이력을 실행 중 보관한다. 최근 8개/열린 탭과 공유하지 않는 추가 보관 추정 128 MiB 한도이며 큰 탭 보관 생략과 오래된 탭 정리를 안내한다. 이 한도는 전체 프로세스 메모리 제한이나 실측 메모리가 아니다.
- F5 전체 파일 새로 고침. 인코딩 선택/조건/강조 유지, 변경된 원문 위치를 원문·소유 헤더·스레드로 확인한다. 중복/삭제 위치는 추측하지 않으며 현재 위치는 가까운 확인된 줄로 복원하고 안내한다. 실패·취소·탭 전환은 이전 상태를 보존한다. 범위·붙여넣기 탭에는 새로 고침을 제공하지 않는다. 같은 원본을 공유한 다른 탭·닫은 탭은 이전 스냅샷을 유지한다.
- Alt+←/Alt+→ 탭별 탐색 이력 최대 100개. 중첩된 검색/문맥 이동을 한 번의 이동으로 기록하며 새 이동은 앞으로 이력을 비운다. 스레드 ID 찾기는 목록만 좁혀 실제 본문 필터와 체크 상태를 유지한다.
- 스레드 행 배경 강도 개선과 보기 메뉴 토글. 기본 켜짐이며 기존 schema 1 표시 설정에 bool만 추가했다. 스레드 마커·선택·검색·문구 강조·문맥·우클릭 대상 표시는 유지한다. 기존 대비 회귀도 통과했다.

## 빌드와 자동 테스트

기존 프로젝트 내부 SDK·NuGet 캐시만 사용했다. `build tests/ThreadLogViewer.Tests/ThreadLogViewer.Tests.csproj -c Release --no-restore -m:1 -nr:false`를 끝낸 뒤 `test --no-build --no-restore`를 실행했다. 테스트 호스트의 로컬 연결을 허용하며 외부 네트워크·실제 창·입력·클립보드를 사용하지 않았다.

| 검증 | 결과 | 기록 |
|---|---|---|
| 최종 Release 빌드 | 경고 0/오류 0 | 프로젝트 내부 SDK, .NET 10 |
| 복원·필터 복구 집중 회귀 | 14/14 통과 | [recovery-focus-r2-v0.7.0.trx](../TestResults/v0.7.0/recovery-focus-r2-v0.7.0.trx) |
| 전체 회귀 | 기존 232개 + 새 39개 = 271/271 통과, 건너뜀 0 | [final-r4-v0.7.0.trx](../TestResults/v0.7.0/final-r4-v0.7.0.trx) |
| 작은 창의 0건 복구 화면 | 내용/스레드 원인 × 다크/라이트 4/4 통과 | 위 전체 회귀의 EmptyRecoveryLayoutTests |

새 회귀는 강조 관리 버튼/편집 바인딩, 배경/마커 렌더, 스레드 찾기, 상시 안내/늦은 진행, 0건 복구/접힌 필터, 탐색 이력/숨긴 검색 문맥, 닫은 탭 상태·개수·공유 메모리 한도, 파일 갱신·인코딩·줄/범위 매핑·중복/삭제·실패·취소·늦은 갱신 차단을 검사한다. 기존 파싱·원본 줄·개행·필터·인코딩·원본 안전 내보내기 회귀를 포함한다.

초기 실행에서 닫은 탭의 스크롤 복원 실패를 발견했다. 선택 직후 무효화된 visual list의 첫 줄을 저장하던 문제와 강제 레이아웃이 대기 중인 스크롤을 소비하는 문제를 확인했다. 실제 오프셋/문서 높이 트리로 앵커를 저장하고, 선택/레이아웃 뒤 현재 세션·문서·보기 버전·커서·선택이 같을 때만 viewport를 재적용한다. 원문·커서·선택·스크롤의 정확한 기대값 회귀를 유지했다. 이전 실패 TRX는 최종 통과에 포함하지 않는다.

## 실측 성능

명령: 테스트 EXE의 `--workbench-benchmark TestResults/v0.7.0/workbench-100MiB-final 100`. 최종 결과는 [workbench-performance.json](../TestResults/v0.7.0/workbench-100MiB-final/workbench-performance.json)이다. 완료·성공 true, 12개 시나리오의 Error는 null이다. 한 프로세스의 단일 실행이며 생성한 파일은 OS 캐시에 있을 수 있다. 런타임 10.0.12. 합성 자료만 사용하며 MainWindow의 실제 로딩·백그라운드 작업·UI 게시·Measure/Arrange/EnsureVisualLines까지 포함한다.

25ms 간격 worker가 Input 우선순위 dispatcher에 게시한 callback의 대기 시간을 측정했다. 이는 숨은 WPF dispatcher 응답이며 실제 입력·FPS·마우스 스크롤 지연이 아니다. p95는 샘플이 적은 경우 최대값과 같으며 여러 실행의 통계로 해석하지 않는다.

| 시나리오 | 총 시간 | dispatcher p95 / 최대 |
|---|---:|---:|
| 100 MiB, 1,603,941줄 열기+배치 | 4,289ms | 511 / 701ms |
| 해당 파일 두 스레드 필터+배치, debounce 100ms 포함 | 357ms | 40 / 40ms |
| 10 MiB 세 파일 개별 열기+배치 | 296 / 317 / 338ms | 87 / 70 / 52ms (각 최대) |
| 세 탭 모두 전환+배치 합계 | 270ms | 93 / 93ms |
| 1 MiB 한 줄 열기+배치, 줄바꿈 꺼짐 | 1,926ms | 1,829 / 1,891ms |
| 동일 줄 줄바꿈 켜기+배치 | 2,212ms | 2,114 / 2,211ms |
| 100,001개 일치에서 첫 100,000개 검색+게시+배치, debounce 180ms 포함 | 322ms | 60 / 60ms |
| 결과 목록 API 스크롤+마지막 결과 이동+배치 | 21ms | 4 / 4ms (1개 샘플) |

실제 reader 진행을 확인한 뒤 읽기를 취소했다. 요청→UI 취소 처리 24.39ms, 처리→작업 종료 69.57ms, 합계 93.96ms였다. 작업이 먼저 끝난 경우를 취소 0ms로 세지 않았고, token 취소·로드 실패 반환·이전 source 유지로 실제 취소를 확인했다. 이 수치는 읽기 단계이며 모든 디코딩/문서 생성/렌더 단계의 취소 지연을 뜻하지 않는다.

100 MiB 열기 직후 프로세스 working set 1,373,216,768 bytes(약 1.28 GiB), managed heap 추정 949,009,304 bytes(약 905 MiB)를 기록했다. 전체 순차 시나리오의 sampled working set 최대는 2,029,244,416 bytes(약 1.89 GiB)이며 캐시·GC heap 보관·이전 시나리오 영향을 포함한다. 개별 탭의 소유 메모리나 유출로 단정하지 않는다.

수명 검사 helper가 끝난 뒤 창을 닫고 강제 GC를 실행해도 모든 시나리오에서 창의 약한 참조가 회수되지 않았다(`ClosedWindowCollected=false`). single-file의 전후 managed 차이는 862,051,152 bytes(약 822 MiB)다. 비표시 WPF/비동기 측정의 참조와 실제 앱의 보관 참조 중 원인은 확인하지 못했으며 메모리 회수나 누수 해소를 통과로 보고하지 않는다. JSON의 별도 기록을 근거로 참조 경로 검증을 후속 과제로 남긴다.

측정에 따른 후속 최적화 순서는 ① 매우 긴 한 줄의 UI 렌더 비용, ② 큰 문서 게시/초기 레이아웃의 긴 dispatcher 점유, ③ 미회수 창의 참조 경로와 원문/투영/문서 전체 보관 메모리다. 한 줄 1 MiB에서는 약 2초의 UI 점유가 남으므로 매끄러운 입력을 확인했다고 보고하지 않는다. 원문 표시/복사/줄 매핑을 바꾸는 임의 절단은 이번 변경에 도입하지 않았다.

## 합성 화면과 실제 GUI

1040×600 DIP 다크·라이트 콘텐츠를 96/120/144/192 DPI bitmap으로 렌더했다. [다크 125%](../TestResults/v0.7.0/workbench-100MiB-final/workbench-small-dark-raster-125.png), [라이트 200%](../TestResults/v0.7.0/workbench-100MiB-final/workbench-small-light-raster-200.png)를 직접 읽어 찾기 입력 안내·필터 상태·행 배경·검색 강조·결과 영역·하단 안내를 확인했다. 8장 구조 기록에서 본문 128 DIP, 결과 180 DIP, 영역 겹침 없음이다.

동일한 작은 창에서 전체 원문 검색 결과를 펼친 채 내용/스레드 필터가 0건인 화면 4장을 추가 검사했다. [내용·다크](../TestResults/v0.7.0/empty-recovery-layout/empty-content-dark-1040x600.png), [스레드·라이트](../TestResults/v0.7.0/empty-recovery-layout/empty-threads-light-1040x600.png)를 직접 확인했다. 복구 버튼을 제목 다음에 배치하고 긴 설명은 스크롤하게 해 본문 높이 128 DIP에서도 버튼과 검색 결과가 겹치지 않는다. 버튼 클릭 경로의 필터 복구와 실제 검색 결과 유지도 자동 검사했다.

visual tree DPI는 100%이며 높은 bitmap DPI는 raster 밀도만 바꾼다. 실제 모니터 125/150/200%, 서로 다른 모니터 이동, 제목줄·포커스·팝업·마우스/키보드 입력, 최소 창에서 모든 보조 패널을 동시에 펼친 상태는 이 이미지로 검증하지 않았다. 실제 GUI 확인은 미실행이며 [직접 확인 절차](FEATURE-TEST-GUIDE.md)를 따른다.

## 독립 검토와 로컬 배포

reviewer가 통합 소스의 요구사항·취소/늦은 게시·공유 원문·갱신 위치·원본 안전 내보내기·표시 설정 호환성을 검토했다. 최종 TRX 271/271, 성능 JSON의 취소·이전 원문 보존, 최종 PNG 4장을 독립 확인했고 새 차단 문제는 확인하지 못했다. 빌드/성능을 중복 실행하지 않았으며 긴 줄 지연과 미회수 창의 원인 검증은 위 한계로 남겼다.

새 배포 경로는 `artifacts/ThreadLogViewer-v0.7.0-win-x64/ThreadLogViewer.exe`와 `artifacts/ThreadLogViewer-v0.7.0-win-x64.zip`이다. 기존 배포·원본·사용자 설정을 보존하며 실행본에는 .NET/WPF/AvalonEdit, 합성 samples와 사용 문서만 포함한다. 개발 도구·캐시·TestResults·실제 로그·user-data를 넣지 않는다. 배포 생성/내용 대조 결과는 `artifacts/verification-v0.7.0.json`에 기록한다. 실행본을 직접 실행하거나 업로드/push하지 않는다.

로컬 publish가 성공했으며 EXE와 앱 DLL의 FileVersion은 0.7.0.0, 포함된 .NET/WPF 런타임은 10.0.12다. ZIP의 513개 파일은 배포 폴더와 모두 SHA-256이 일치하며 금지된 사용자 자료·개발 산출물은 0개다. ZIP 자체의 크기와 SHA-256은 위 검증 JSON을 따른다.
